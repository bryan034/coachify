# Saved CV processing and effective evidence

Local model testing: with `APP_ENV=development`, `CV_LLM_ALLOW_HTTP=true` and a
known localhost/Docker-host endpoint, model/key configuration supports keyless
Ollama requests and omits stored cloud keys. Local extraction uses 120-second
HTTP timeouts; interpretation and conversation use 60 seconds, below their
existing operation leases. Cloud authentication/timeouts, record ownership,
model admission and source-grounded validation remain unchanged.


## Ownership and versions

CV owns `cvs` documents and operational `cv_selections`, `cv_conversations`, `cv_upload_capacity` and `cv_model_usage`. Profile owns sessions, onboarding/planning inputs and account-level manual capability declarations. Only the session-derived UUID identifies the owner; every source, operation and mutation query includes it. No service reads another service's database. No binary, filesystem path, source hash or provider credential is returned.

Each CV has a write `version`, `extraction_version`, and `effective_version`. A private `revision` fences every database change, including lease/receipt changes that do not change user facts. Selection and declarations have their own versions. Repeated requests replay by mutation UUID and fingerprint; conflicting key reuse returns 409. Actual no-op edits/removals and skip-only state do not advance `effective_version`. Selection is never changed by upload, extraction or retry.

Corrections retain original evidence and source item identity. Canonical skill IDs use `skill:` followed by NFKC-normalized, whitespace-collapsed, casefolded names; punctuation remains meaningful. An explicit skill rename updates its canonical label while keeping its source claim ID. Matching names never delete or combine source claims. Claim-level provenance is not independent verification.

## Upload, extraction and recovery

Default maximum is 10 MiB, returned by `/policy` and enforced against file bytes inclusively. The API accepts PDF/DOCX multipart uploads with a UUID `mutation_id`; renamed/empty/unsupported files fail clearly. Complete parsing happens in a child process with a 20-second wall deadline, Linux CPU/address-space limits, at most 100 PDF pages, 1,000 ZIP entries, 32 MiB expanded DOCX content, and 100,000 extracted characters. Encrypted files, unsafe XML, macros and image-only CVs fail with recovery guidance. OCR is unsupported.

Upload admission also reserves saved-record and original-byte capacity before writing a file. Defaults are 50 saved CVs and 100 MiB of retained original bytes per account, with 10,000 saved CVs and 10 GiB of originals across the service. Saved-record capacity includes failed uploads and remains charged after the original expires; byte capacity is returned only after physical deletion. Exact upload retries reuse the same CV identity/reservation. Exact-byte resupply of an existing original does not consume a second file allowance. `/policy` exposes `max_saved_cvs` and `max_stored_original_bytes`. A full limit returns 409 with `code=cv_capacity_exceeded` and recovery guidance; uncertain admission returns 503 with `code=cv_capacity_unavailable`.

`GET /api/v1/cv` returns lightweight metadata, the unchanged explicit selection and `next_cursor`. `limit` defaults to 25 and accepts 1–100; the opaque `cursor` advances by creation time and CV identity. MongoDB projects summary fields before loading the page, without reading full evidence/history aggregates. A selected CV may be outside the current page and remains directly readable by ID. Clients must follow `next_cursor` when they need the remaining list.

Parsing emits transient page/paragraph blocks. The compatible JSON-mode model adapter has a bounded response and duration; validates finish reason, schema, finite nonnegative known months, source IDs, exact excerpts, relationships, and usable nonempty extraction. Missing sections, including all skills, are valid when another useful item exists. The model receives source text as untrusted data. Local validation proves structure and cited excerpts; semantic extraction accuracy still requires evaluation against representative, labelled CVs.

Structured items, bounded evidence (500 characters per excerpt), provider/model/prompt/schema metadata and source versions are saved. Full parsed text and prompts are not persisted or logged. Source IDs are derived from CV identity, section and exact evidence; similar names never grant reuse across CVs. Model output is published atomically in the owner document only by the current unexpired worker lease. The worker polls persisted jobs, reclaims expired leases, and exposes an actionable failure after three interrupted attempts. A later explicit retry is idempotent. Failures preserve prior extraction and overlays.

Originals are mode-0600 files under a mode-0700 service-private directory with generated UUID names. They are retained for 24 hours for retry, then a lease-aware cleanup claim removes bytes before marking deletion. Interrupted deletion is recoverable; untracked files older than one hour are removed. Expired originals require exact-byte resupply using `cv_id` and `expected_version`; a changed file must be a new CV. The API never reconstructs deleted original bytes or exposes a public file URL.

The standalone-MongoDB admission ledger is one journaled CAS document with at most 20,000 fixed-shape upload entries (CV reservations and recoverable legacy orphans) and a 12 MiB safety bound. It derives owner/global totals from those entries, retaining pending reservations across crashes instead of expiring uncertain counters. A bounded set of POSIX lock files serializes each CV's reservation, deterministic temporary file, publication, resupply and deletion across processes. Recovery acquires that same lock and checks the durable record before deleting an abandoned file or releasing its reservation. MongoDB uncertainty can conservatively retain capacity; it never permits releasing bytes before unlink. Cleanup and ingestion advance through bounded metadata pages and load one current CV at a time, isolating individual record failures so another owner's work can proceed.

On first use, a bounded metadata bootstrap accounts for existing records, actual file sizes and otherwise untracked originals/partial files. Existing records are preserved and readable even when they exceed new limits; new admission then fails closed. Exceeding the hard ledger bound or encountering unsupported legacy ownership requires administrator review. All CV processes must use this implementation and share the same persistent POSIX-locking upload volume. Stop older writers before the initial ledger bootstrap; network filesystems without reliable shared locks and mixed-version writers are unsupported. Lock files are never deleted during service operation, because replacing their inodes would break mutual exclusion.

Same-source reprocessing keeps corrections, removals and answers when stable source identities and interpreted attributes match. If a model changes a retained source identity, skill relationship or structured attribute, the previous result and a bounded structured candidate are saved for comparison. The user can keep the previous extraction or accept the candidate after explicitly archiving or mapping every affected statement to a same-kind item. No mapping is selected by name. Corrections/removals may be reapplied only by this explicit choice; explanations retain their original origin/history and require fresh interpretation against the new evidence. A newly uploaded replacement can explicitly compare a previous ready CV before acquiring its own edits or answers. Discarding a comparison remains possible if the old CV changes. Neither comparison nor acceptance changes the selected CV automatically. Pending comparisons, processing and failed sources cannot supply new capability inputs.

History and idempotency receipts remain embedded with full source ownership. Before user content, extraction or retained history exceeds 12 MiB, the API rejects it with guidance to retain the historical source and upload a new copy; it never silently truncates history. Worker lease, bounded failure and original-deletion bookkeeping have an explicit additional 8 KiB allowance so a full source cannot block cleanup. Oversized extraction publishes a bounded failure against the prior record without replacing its evidence/history. This MVP does not provide an archive/delete UI or unlimited lifetime edit storage.

## Clarification and corrections

The target provider boundary accepts only server-fetched confirmed specific-job requirements or exploration guidance with ID, type, version, canonical skill IDs and selection revision. CV forwards the owner's revocable bearer to Career's `GET /api/v1/career/targets/selected-context` for reads and `GET /api/v1/career/targets/{id}/confirmed-context?expected_version=N` for preparation. The private client uses a five-second total deadline, bounded 1 MiB strict JSON (at most 40 skill IDs, including Unicode normalization expansion), no proxy environment or redirects, and validates required metadata and canonical skill identities. A browser cannot submit target skills or confirmation to manufacture question relevance. Career unavailability is an explicit failure; only an explicit null selected context produces a deferred response.

Question responses carry `cv_version`, the current context and `prepared`. A successful prepare stores the target ID/type/version/selection revision and extraction version in the owner CV, even when no questions are relevant. Thus empty prepared results mean there is no current material extracted uncertainty; they do not request another target. Old CVs without this preparation marker require explicit preparation while preserving existing answers and skips. New extraction versions and target selections require preparation again. Preparation changes no capability facts. The endpoint revalidates the selected target after saving; a switch reports a conflict without deleting source-bound history. These are captured cross-service snapshots, not a distributed transaction.

Only material, extracted uncertainties matching confirmed context produce questions. Skill overlap establishes skill relevance. Confirmed qualification/date conditions additionally require the specified item kind and a whole-phrase subject match in that source. Condition-only targets are supported; unknown relevance is deferred. Question identity depends on source and uncertainty, not target or prompt wording. Saved answers/skips survive target changes. Pending questions are filtered against current effective uncertainty and relevance; an answer resolving multiple attributes suppresses the obsolete prompts. Partial answers may lead to a distinct remaining question, while an explicit inability to clarify permits continuation without repeating that uncertainty. Reads never generate questions or mutate facts.

Answers accept up to 4,000 characters including partial knowledge and “I do not know”, with no proof requirement or extra activity confirmation. The original explanation is saved before provider execution. Answer receipt, interpretation processing and factual resolution are separate states. A bounded CV-owned adapter uses the existing extraction provider settings and validates typed output, exact source/answer revision, supporting answer excerpts, canonical skills, field scope, finite duration, date precision and metadata. Model instructions and answer content cannot directly patch arbitrary CV fields. Schema/excerpt checks do not prove semantic entailment; live-model quality still needs separate evaluation.

Successful interpretation updates individual source-linked skill claims: personal, team-only, observed, denied or unknown attribution, plus explicitly stated assistance, proficiency and duration. An explicitly named new personal skill can be added under that CV item; it is not silently added to account-level manual declarations. Team/observed/denied support is excluded only at that source and its affected derivations. Other supporting sources and unrelated known attributes survive. Unknown never becomes zero, mastery or global absence. Conflicting known values remain explicit rather than being summed or averaged. The review and matching UI use the same effective skills as downstream inputs. Original CV evidence, literal explanations and interpretation provenance remain available. Corrections and validated interpretations are projected in their actual change order, per field. A newer clarification can resolve support made uncertain by an earlier correction; a later correction still takes precedence. Date-only edits do not make an unrelated personal-contribution answer obsolete. Internal correction field sequences preserve this ordering, with retained history used for older records and conservative correction precedence when that history is unavailable.

Pending/failed current interpretations remain visibly unresolved and are rejected by target-bound input assembly. An existing successful interpretation remains current saved evidence while a replacement answer on the unchanged source is pending; it must not be presented as the new answer's resolved result. Retry uses a separate mutation receipt, an invocation token and a 90-second execution lease. A live pending claim cannot start another retry; an expired interrupted claim can recover. Only the winning claim can call the provider and publish against matching source/answer/document revisions. Each service process permits at most two concurrent interpretation calls; capacity failures preserve the answer and offer retry. No automatic reinterpretation of older answers occurs; the user can explicitly interpret them.

A material title/description correction or removal marks affected questions and answers historical. Their interpretations and clarified statements no longer enter effective facts, fingerprints or current pending/unanswerable guards. Preparation is invalidated, and fresh source-bound questions can be prepared or answered through chat. Fresh prompt keys include the retired question identities for that item/uncertainty, so repeated preparation stays stable and an edit/revert cannot revive an old question. Literal answers and interpretation history remain readable. Narrow date/proficiency/duration edits affect only their question category; canonical case/whitespace-only display renaming preserves valid facts. Reconciliation derives each transferred answer's identity from its source CV/event and reviewed target, remaps follow-up links and retains provenance. It rejects ambiguous duplicate source IDs instead of silently collapsing statements.

Skip preserves prior answers and supported facts, creates no capability/absence, and does not advance effective fact versions. Rewording an answer with unchanged interpreted facts or retrying receipt metadata likewise does not change the capability projection. Corrections/removals retain source history and invalidate affected questions; dependent support is recomputed per skill while independent evidence and Profile declarations remain intact. Optional start/end dates retain YYYY, YYYY-MM or YYYY-MM-DD precision, can be explicitly cleared, and support an ongoing flag. Chronology is rejected only when the known intervals establish an impossible order. A date range never automatically establishes skill experience months. Extraction and interpretation both reject date precision or ongoing status unsupported by their cited source excerpt. Reapplying a correction to replacement evidence validates the combined dates before publishing; incompatible choices leave the saved comparison available for another choice.

## Saved conversational review

The additive conversation API stores bounded, owner-scoped text history. Opening a conversation resumes the latest segment for the exact CV ID; a null CV reference supports manual capabilities before upload without manufacturing a CV. The transcript and action receipts are operational metadata, never a second capability authority. Their revision advances independently of CV versions, so a side question or history read cannot invalidate an evidence interpretation. Previous saved answers remain identifiable as existing clarifications rather than invented historical dialogue.

Messages accept up to 4,000 characters. The coordinator durably stores the user message and a pending receipt before scheduling provider work. HTTP responses return that pending state promptly; clients poll history. Each process tracks at most 16 background operations and shares the existing two-provider-call capacity with clarification interpretation. Process shutdown cancels tracked coordination; interrupted action leases become explicitly retryable after 90 seconds. Bearers remain in memory only and are revalidated before deferred writes and again after interpretation before publishing facts. No credentials, full provider prompts or private CVs from other contexts are stored in the transcript.

Conversational routing uses the existing provider settings and a constrained action schema, with a 25-second deadline and 256 KiB response limit. Input contains the full latest message, short identity summaries for this CV, at most one focused source, bounded recent-message context and confirmed target labels. Input JSON is capped at 96 KiB. The router cannot choose mutation keys, versions, arbitrary API paths or records outside the supplied source list. All proposals validate before execution; unknown source references, unsupported excerpts, malformed output and execution-control fields fail while preserving the message. Grounded side-question replies produce no domain actions. These controls establish structure and access boundaries, not real-model semantic accuracy.

The original full user message reaches interpretation, even when a router returns a narrower excerpt, so routing cannot strip negation or qualifications from the interpreter input. The first answer can resolve its prepared question. Subsequent context and confirmed explanation corrections create separately identified source-bound clarification events linked to earlier questions. Each event retains its own original message and changes only the fields supported by its interpretation. Existing chronological field projection preserves prior contribution, guidance and independent evidence without concatenating an unlimited answer or silently truncating a 4,000-character field. Further statements for a source with unfinished interpretation wait for that earlier operation to be resolved. Explicit user-initiated factual context can be recorded without inventing target relevance.

Ordinary answers apply through the established interpretation lifecycle. Item corrections, removals and manual capability additions are proposals requiring explicit Save or Cancel. Choosing between ambiguous sources does not itself confirm a destructive change. Matching manual capabilities require an explicit attach/distinct choice; writes go through Profile's authenticated capability API, retaining its versions, source validation and mutation receipts. A chat message containing several actions exposes each outcome separately. Successful actions are not repeated when another action fails. Exact retained mutation bodies recover a lost return after a domain write, including a Profile save, a guided or conversational skip, and question preparation. A retried skip retains its original question identity even after resuming or advancing to another question. Guided recovery retains the original confirmed-target binding. No cross-service atomic transaction is claimed.

Every action captures CV/extraction, source selection and confirmed-target identity. Concurrent edits or changed selections reject stale actions and retain messages for review. Opening or reading a conversation revalidates Career context, clearing obsolete active prompts while retaining factual answers. Career unavailability preserves readable history and reports a context error. No-target/manual-only conversations can still accept manual declarations; target-dependent prompts remain deferred. Guided review/continue prepares existing relevant questions, and skip never removes a newer saved answer. Preparing more questions waits while interpretation is unfinished.

History is paginated (40 messages by default, up to 100 per request). A segment stops accepting new turns when two more messages would exceed 500, or its stored size reaches 6 MiB; the existing welcome message means a normally filled segment stops at 499. The 8 MiB operational-document safety limit reserves room for outstanding action receipts. Full segments remain readable and their pending proposals can still finish or cancel. Reopening after unfinished actions are resolved creates a new segment linked to the previous one; listing exposes all retained segments, up to 100 per owner/CV context. There is no automatic transcript expiry or deletion in this slice. Original upload-file retention remains a separate policy.

CV history retains its existing 12 MiB pre-publication limit. Direct answers, retries and chat now share a durable pending-result reservation. Before accepting a literal answer, the same atomic CV write reserves a future clarification/overlay snapshot and 512 KiB for its bounded interpretation/publication; multiple pending results also reserve the growth of later snapshots. Other user writes cannot consume that space. Each pending generation additionally reserves 64 KiB for retry receipts, charged conservatively at 1 KiB per interrupted retry. Retry claims preserve the existing literal answer and snapshots without copying the same content again; definitive result publication retains its snapshot. If repeated interrupted claims exhaust their receipt allowance, the answer becomes an explicit failed result rather than staying permanently pending. A new explicit retry remains subject to ordinary capacity admission. Stale providers cannot release another invocation's reservation; definitive results and source invalidation release only their own reservation. Worker housekeeping retains its separate actual-byte allowance.

Before creating a chat question, a preview accounts for the question/answer snapshots, literal text and shared result reservation. Chat-created clarification events also stop before exceeding 800 total clarification records. Hitting either limit leaves the message and previous evidence intact with guidance to retain the historical source and use a new saved source. No existing history is truncated or migrated, and no unlimited retention is implied. Cancelling an unattempted proposal changes no CV facts. Cancelling retry after an attempted save stops future processing and explicitly warns that previously saved facts/explanations remain; it does not claim to roll back a write or resolve an unfinished interpretation.

The conversation supports existing C-series actions. It does not introduce voice, arbitrary new project/employer/education creation, Career target editing, assessment admission or roadmap generation. Existing source, declaration and correction APIs remain compatible.

## Model-call admission

Extraction, conversational routing and clarification interpretation share one CV-only admission boundary. The defaults are 120 provider-call attempts per account and 2,000 globally per UTC day, with one active call per account and three across all CV processes. A factual chat turn may use one routing call plus one interpretation call; these limits count provider attempts, not messages or money. Existing per-process limits on shared routing/interpretation remain in force. `/policy` exposes the account's `max_model_calls_per_day` and `max_concurrent_model_calls`.

One journaled `cv_model_usage` document contains a monotonically revised daily counter and at most 10,000 hashed-owner counters. A newer UTC day resets the counters; a backwards clock never resets them. Invalid or uncertain counter state fails closed. An attempt is reserved immediately before the synchronous provider callback; failed or ambiguous attempts are not refunded. Disabled providers, parser failures, reads, question preparation, skips, explicit local edits and successful receipt replays do not consume attempts. Inputs are saved independently: denial leaves the upload/message/answer available with a clear retry explanation.

Concurrency uses a separate private `.model-slots` directory with one gate file and a fixed bounded slot pool. The short gate coordinates nonblocking slot inspection and exactly 64-byte owner-hash tags; it is released before database or provider I/O. The selected OS lock remains held inside the synchronous callback, even when an async waiter is cancelled. Process death releases the lock without waiting for a lease timeout. Malformed busy-slot ownership fails closed; unlocked stale tags are safely overwritten. Slot files are never unlinked during operation. All processes must share the POSIX-locking upload volume and identical limits; stop old processes before changing the slot count. This does not introduce Career budgets or a provider-specific API.

## Downstream admission

`capability-input` retains its source-only compatibility contract: it requires exact CV, selection and declarations versions and a ready explicitly selected CV. Its additive fields include the CV write version, explicitly named upload-time Profile version and assessed manual-source link states. The legacy `profile_version` still means upload-time provenance, not current Profile background. The legacy detail `review_required` is only a coarse source-change indicator, not a saved-result freshness decision.

`analysis-input` adds a version-2 envelope containing that complete source snapshot and the owner’s selected confirmed target, type, version and selection revision. It rejects missing/mismatched targets, pending comparisons or unresolved interpretation execution, and rechecks source, selection, declarations and target during assembly. This produces a captured version vector, not atomic assessment admission. The future Career consumer must save the exact immutable inputs and revalidate at admission; result-specific stale assessment/roadmap tracking remains outside this C-owned slice. Neither endpoint starts an assessment or generates a plan.

Manual declarations remain Profile-owned. CV assesses their attachment against the chosen source's semantic fingerprint rather than the whole CV write version. Link states distinguish standalone, current, changed, removed, unavailable and older unverified relationships. Reads do not mutate the declaration. Explicit Profile detach/reattach preserves statement and contribution history; repetition is not independent proof.

## Configuration

Required: `MONGODB_URI`; optional `MONGODB_DATABASE` (default `elo_cv`), `PROFILE_SERVICE_URL` and `CAREER_SERVICE_URL` (default `http://career-service:8000`). Career configuration is an HTTP(S) service origin without credentials, path, query or fragment. `CV_STORAGE_PATH` must be private persistent storage, mounted at `/app/uploads` in Compose. `CV_MAX_FILE_BYTES` defaults to 10 MiB; standalone overrides up to 20 MiB require a matching gateway body limit plus multipart overhead. Compose intentionally fixes 10 MiB with an 11 MiB gateway request cap.

Capacity settings are `CV_MAX_SAVED_CVS_PER_OWNER` (50), `CV_MAX_SAVED_CVS_GLOBAL` (10,000), `CV_MAX_ORIGINAL_BYTES_PER_OWNER` (104,857,600) and `CV_MAX_ORIGINAL_BYTES_GLOBAL` (10,737,418,240). Record ceilings accept 1–20,000; byte ceilings accept 1–1 TiB. Lowering limits does not remove records or originals. The first ledger bootstrap needs the existing private upload volume mounted at its normal path. Configure these server settings through the deployment environment; no environment file is modified by this change.

Model settings are `CV_MODEL_CALLS_PER_OWNER_PER_DAY` (120), `CV_MODEL_CALLS_GLOBAL_PER_DAY` (2,000), `CV_MODEL_CONCURRENT_PER_OWNER` (1) and `CV_MODEL_CONCURRENT_GLOBAL` (3). Daily ceilings accept 1–1,000,000, with the owner ceiling no larger than the global ceiling. Global concurrency accepts 2–32, and owner concurrency must be strictly lower to leave another account capacity. Compose forwards all these settings explicitly. Admission is independent of the configured provider/model and does not call a provider during tests.

`CV_LLM_BASE_URL` defaults to `https://api.groq.com/openai/v1`; `CV_LLM_MODEL` and `CV_LLM_API_KEY` are server-only. HTTPS, no URL credentials, no query, no redirect following. HTTP fixture URLs require both `APP_ENV=development` and explicit `CV_LLM_ALLOW_HTTP=true`; production always rejects HTTP. No model is hardcoded and no paid-provider call is required to run tests. Port 8000; access logs disabled in the Docker command.

## Separate Assessment consumer — 30 October 2026

The additive `/{id}/assessment-input` export applies the selected-source/version/declarations guard from capability-input and rejects unfinished interpretation. Assessment separately binds the full Career target and revalidates all sources. This differs from the explicitly confirmed-target analysis-input envelope used by earlier consumers; it does not acknowledge a target for clarification or write any capability facts. Public skills resolve `canonical_skill_id`/`skill_registry_version` through the shared bundled package while retaining their original name-based skill keys and source histories.
